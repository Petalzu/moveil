# 从识别隐私，到认真对待每一次分享：墨隐 MoVeil 团队参赛历程

> 整理于 2026 年 9 月 29 日。本文依据项目开发与交付记录，以团队视角回顾探索过程；按开发阶段叙述，不代表跨越了特定天数。

## 一、从一个贴近日常的问题出发

分享一张截图之前，我们常常需要检查：姓名有没有遮住？联系方式是否还留在角落？一段看似普通的文字，会不会暴露不适合公开的信息？

墨隐 MoVeil 的开发，就是围绕这样一个具体的问题展开的。我们希望借助 AI，帮助使用者发现图片中的敏感信息，并把识别结果落实为真正的图像遮挡。

最初，这个想法可以用很短的一句话概括：识别文字，找出隐私，再把它遮住。真正动手以后，我们才逐渐理解，这句话里的每一步，都有各自需要解决的问题。模型找到了敏感内容，不代表程序找对了位置；画面上出现了黑框，也不代表所有需要保护的文字都被完整覆盖。

这也让项目的目标变得更加具体：我们要做的，不只是一张看起来处理过的图片，而是一条能检查、能补漏、能追溯的辅助脱敏流程。

## 二、第一个原型，让想法落到了图片上

早期原型采用本地 OCR 提取文字，再由通用大模型判断其中的敏感内容，最后由程序执行遮挡。这个阶段，我们首先要解决的是让各个环节真正连接起来。

模型调用、文字识别、坐标映射、图像输出，单独看都有现成工具，但把它们组合起来，并不是简单地接上几个接口。不同环境的依赖兼容、模型返回结果的格式、文字与图像位置的对应关系，都需要逐一核实。项目也经历了 Python 环境调整：能运行并不等于符合依赖要求，稳定的基础环境同样是作品的一部分。

当原型能够输出遮挡后的图片时，项目有了可以直接观察和讨论的结果。但对照原图检查，又会发现一些不容易从接口返回中看出的问题：有的内容漏掉了，有的黑框遮到了旁边的字，有的判断虽然指向正确类别，却没有落到正确位置。

第一个原型的价值，不在于它已经足够好，而在于它让问题从抽象的设想，变成了可以逐项定位的现象。

## 三、一次重要的调整：不再让模型包办所有事情

早期方案需要模型选择 OCR 词元。随着调试深入，我们发现，这相当于让模型同时承担两件事：理解哪些文字敏感，以及准确指出这些文字在程序中的编号。文字被拆分、重复或跨行后，两件事叠在一起，很容易产生错位。

我们尝试过加强校验，让模型给出能够与原文对应的证据。这样做能拦住一部分错误输出，却不能让遗漏的内容自动出现。某些运行因此不再生成处理图，而是明确失败。

这段经历让我们开始区分两种进步：一种是识别得更完整，另一种是出错时不把结果当成成功交出去。它们都重要，但不能互相替代。

随后，方案转向更清晰的职责划分：让模型返回原文中的实体字符串和标签，再由程序完成严格的文字匹配与位置映射。与其不断要求模型“再准确一点”，不如先减少它不必承担的不确定性。

这成为整个开发过程中的一个关键转折。我们不再只关注提示词如何表达，也开始重新审视：哪些任务适合交给模型，哪些任务应该交给确定性的程序逻辑。

## 四、从一张图走向一组图，接受并不顺利的迭代

当单张样例的处理效果改善后，下一步自然是把流程放到更多图片上。也正是在这个阶段，开发不再呈现出“每改一次就更好”的样子。

在一张图上有效的方法，遇到不同内容和断行方式，可能又会出现遗漏。我们尝试了分块、限制标签和补充规则，但组合后的结果并没有稳定优于原方案。有些调整解决了局部问题，却带来了新的误判和误遮挡。

这让我们更加重视如何看待一次实验。一次修改有合理动机，不代表它就应该进入默认流程；某个样例变好了，也不能代表整个方案变好了。

因此，开发中保留了失败记录，没有只挑选表现好的图片来讲述结果，也没有为了让结果显得合格而降低原有要求。这些记录后来成为继续判断方向的依据：哪些问题值得继续修，哪些尝试暂时不应成为主路。

参赛开发不只是积累功能，也包括学会放下没有被验证有效的方案。

## 五、最有启发的一次排查：文字认对了，为什么还是遮不住？

在探索专用实体识别模型的同时，我们也进行了 OCR 对照。一个很有启发的现象是：文字识别有所改善，最终的遮挡效果却明显退步。

如果只看识别出的文本，这个问题很难解释。只有把原图、文字框和实际遮挡区域放在一起检查，才能看到：文字框未必完整包住了字形，位置上的细小偏差，会直接变成脱敏结果里的漏字。

于是，排查从“是不是模型没识别出来”，推进到了“坐标到底怎样生成、怎样对应回原图”。我们查看了相关实现，验证框的含义，再尝试将一路 OCR 的行文本与另一路经过检查的几何信息结合起来。

这个混合方案修复了明显的几何问题，但没有因此解决所有语义遗漏。它带来的收获，比单纯换一个组件更深：识别文字、理解实体和覆盖像素是相互关联、却不能混为一谈的三个环节。

从这以后，面对不理想的结果，我们有了更明确的排查顺序，而不是把所有问题都归结为“模型还不够强”。

## 六、走向本地识别，也重新认识项目的边界

随着专用 NER 方案接入，项目逐步转向本地实体识别，并在发布主路中采用 NVIDIA GLiNER-PII。NVIDIA 的模型与合成数据，也由此成为项目开发和验证的重要组成部分。

这一步不仅涉及模型选择，也涉及如何把模型稳定地放进应用：独立管理运行环境、固定版本、校验文件、处理窗口与标签，以及保留可追溯的配置记录。默认主路不再依赖把 OCR 文本发送给远端通用模型；依赖与权重准备完成后，可以在本地进行推理。

识别覆盖有了明显改善，但这并没有让我们把项目定义为“已经解决隐私问题”。漏检、标签错误和误遮仍然存在，已有样例也不足以证明它能应对各种真实文档。

因此，我们最终采用了更准确的定位：图像隐私识别与辅助脱敏。这里的“辅助”不是一句附带说明，而是直接影响产品设计的前提。

## 七、从脚本走向使用流程，把人工复核认真做进去

命令行能够生成结果后，另一个问题变得突出：使用者怎样发现遗漏，又怎样修正它？

我们逐步把处理流程放进本地浏览器界面，让原图与结果可以并排查看，让检测框和标签能够辅助检查，并支持拖动补框、保存新版本和下载处理后的图片。后来又加入样例批量处理和单图上传，让演示不再只是打开一张已经生成的结果图。

这些功能看起来没有更换模型那么显眼，却决定了作品能否被真正操作。自动结果不够完整时，使用者需要一条清晰的补救路径；保存之后，也需要知道自己拿到的是哪个版本。

在实现中，我们坚持直接修改输出像素，而不是只在页面上覆盖一层视觉效果；同时检查输出、清除原图元数据，并保留“待人工复核／未批准”的状态。

这段开发让我们意识到，人工复核不应该只是说明书末尾的一句提醒。既然系统存在不确定性，就应该把检查和修正的入口做到产品里。

## 八、准备参赛材料，也是重新理解作品的过程

当项目从 Privacy Image Agent 整理为“墨隐 MoVeil”，工作也从功能实现延伸到了命名、说明、许可和演示材料。

我们需要向没有参与开发的人讲清楚：它解决什么问题，怎样使用，哪些结果已经验证，哪些能力还没有被证明。这迫使我们重新梳理此前的每一次尝试，把研究过程、应用发布和视频材料分别整理，而不是把所有实验产物一起当成交付物。

演示素材来自实际服务操作，包含上传、处理、对照、补框和导出，再通过关键帧剪辑呈现主要流程。视频可以帮助观众理解操作，但不能替代完整测试，也不能把剪辑后的节奏当作真实运行速度。

许可与来源说明同样是这一阶段的重要工作。自有源码、第三方数据和模型分别适用不同许可，需要明确归属；安装说明、模型准备和数据重建也需要留下可供后来者理解的路径。

从开发者视角看，代码能够运行似乎已经接近完成；从交付视角看，别人能否理解、复现并正确使用它，同样需要投入。

## 九、这段参赛经历留给我们的东西

回顾墨隐的开发，最有价值的并不是找到一个能够包办一切的模型，而是逐渐形成了一种更踏实的工作方式：先把流程跑通，再用实际结果检验假设；出现问题时拆开环节，保留证据；局部改善之后，继续检查它是否带来了新的代价。

围绕识别、评测、交互和交付展开的工作，也让项目从一个技术想法，变成了具有完整使用路径的原型。实验记录、测试和核查清单，把这些环节连接起来，让每一项对外描述都有可以回看的依据。

截至本次整理，墨隐已经形成可运行的本地辅助脱敏流程，但自动质量门槛仍未全部通过。目前验证主要围绕 Windows CPU 环境中的干净横排合成文本图展开，复杂版面、中文正文和其他运行环境仍需要进一步验证；发布整理也不等于已经正式提交或上线。

这些边界没有削弱这段经历的意义。恰恰相反，它们让我们更清楚下一步应该做什么，也让我们学会不把“演示成功”当作“问题已经解决”。

**如果用一句话概括这次参赛开发：我们从“让 AI 找到隐私”出发，逐渐学会把识别、验证、人工检查和交付放在同一条流程里，认真对待每一张即将被分享的图片。**
